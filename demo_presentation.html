Phase 1 — Data Collection, PDF Extraction & Corpus Cleaning
⏱ 2–3 min

[Introduction]
Hello, I am Kishor Bharat, student ID 2024TM05030, contributing 30% to this project. My responsibility was Phase 1 of the pipeline — building a clean domain corpus from raw PDF source files, which is the foundation every subsequent step depends on.

[Task 1 — Data Collection]
We collected two regulatory PDF documents as our source data: AIS 175 — the Indian adaptation of the World Harmonised Light-duty vehicles Test Procedure (WLTP), and AIS 197, which covers related emission standards. These documents are dense technical regulatory text — exactly the kind of domain corpus a small language model needs to learn specialised vocabulary and sentence structure. The PDFs were placed under the data/pdfs/ directory.

[Task 2 — PDF Extraction Pipeline]
For extraction I implemented the function extract_pdfs_to_raw_text() in our pipeline. It iterates through every PDF in the folder, opens each file using PyMuPDF — with an automatic fallback to pdfplumber if PyMuPDF is unavailable — and reads the text of every page one by one. Each page is tagged with a FILE separator and a PAGE marker before being written into a single raw output file: data/processed/ais175_raw.txt. This page-by-page tagging is deliberate — it preserves the exact page boundaries from the original document so that extraction errors can be traced back to a specific page.

[Task 3 — Corpus Cleaning]
Raw PDF extraction always contains noise: standalone page numbers, table-of-contents lines, repeated headers like "Draft AIS 175 / March 2025", separator lines, and broken hyphenated words split across lines. I implemented clean_raw_text() to remove all of this systematically using regex rules. The function strips FILE and PAGE markers, removes lines that are purely numeric, removes known heading noise using exact string matching, repairs hyphenated word breaks, normalises excessive whitespace, and collapses multiple blank lines. The final output, data/processed/ais175_clean.txt, is over 120,000 characters of continuous, readable regulatory text.

[Justification of Inferences]
Why does this matter for downstream results? The quality of the language model is directly bounded by the quality of its training corpus. If we had fed the raw text — full of "Page 42", "Annex B", "Draft March 2025" noise — those tokens would have polluted the vocabulary and confused the model. By cleaning before tokenisation, we ensure the tokenizer learns meaningful subwords from actual sentence content, and the training signal comes from real regulatory prose. This is why even the small 15-million-parameter model we trained can generate domain-specific terms like "annex", "correction vehicle", "paragraph 3", and "vmax" in its outputs — it learned from a clean, coherent domain corpus.

Saurabh Mani  2024TM05067 · 25%
Phase 2 — Custom BPE Tokenizer Training & CLM Dataset Generation
⏱ 2–3 min

[Introduction]
Hello, I am Saurabh Mani, student ID 2024TM05067, contributing 25% to this project. My responsibility covers Phase 2 — training a Byte-Pair Encoding tokenizer entirely from scratch and preparing the Causal Language Modelling dataset that the model trains on.

[Task 1 — Why a Custom Tokenizer]
Off-the-shelf tokenizers like GPT-2's tiktoken are trained on general internet text. Our corpus is highly specialised — it uses abbreviations like WLTP, PEMS, OBD, ISC, units like vmax and km/h in formatted equations, and regulatory citation patterns like "paragraph 4.3" and "Annex C6". A general tokenizer would split these into meaningless character fragments. By training our own BPE tokenizer from the cleaned corpus, the merge rules are learned directly from our data, so domain terms get their own dedicated subword units.

[Task 2 — BPE Implementation]
I implemented train_bpe_tokenizer_from_scratch() following the original Sennrich et al. BPE algorithm. First, every word in the corpus is split into individual characters with an end-of-word marker </w> appended. Then the algorithm counts all adjacent symbol pairs across the vocabulary, finds the most frequent pair, merges it into a single new symbol, and repeats. We continue merging until the vocabulary reaches 4,096 unique tokens or the minimum frequency threshold drops below 2. Four special tokens are reserved — <pad>, <unk>, <bos>, and <eos> — and the remainder is filled by the most frequent subwords ranked by corpus frequency. The final vocabulary and merge rules are saved as vocab.json and merges.txt.

[Task 3 — CLM Dataset Generation]
For Causal Language Modelling, the training objective is to predict the next token given all previous tokens. I implemented this in the CLMDataset class. The entire cleaned corpus is tokenised into a flat list of integer IDs. The dataset then slides a block-size window across those IDs. For each window, the input X is tokens 0 through N−1 and the label Y is tokens 1 through N — a one-position shift. This shift is the CLM objective: the model must predict position T+1 given positions 0 to T. We also performed a 90 / 10 train–validation split so training loss and validation perplexity can be tracked independently.

[Justification of Inferences]
The BPE tokenizer's effectiveness is visible in the inference outputs. The generated text contains domain-specific tokens like "annex", "paragraph", "correction", "vmax", "vehicles" and "km" — these are exactly the subwords that appear frequently in AIS 175 and were therefore given dedicated IDs by our tokenizer. If we had used a character-level tokenizer, the model would have struggled to learn word-level semantics within the limited parameter budget. The vocabulary size of 4,096 was chosen deliberately: large enough to cover domain terms, but small enough that the token embedding table remains compact for a 15M model.

Phases 3–5 — Transformer Architecture, Causal Masking & Training Loop
⏱ 2–3 min

[Introduction]
Hello, I am Saranjit Singh, student ID 2024TM05027, contributing 25% to this project. My work covers Phases 3, 4, and 5 — implementing the full decoder-only transformer model, the causal attention mechanism, and the complete training loop with checkpointing.

[Task 1 — Input Embeddings (Phase 3)]
Every token ID produced by the tokenizer is first mapped to a 384-dimensional vector through a learned token embedding table. To give the model a sense of position — because transformers process all tokens in parallel and have no built-in notion of order — I added sinusoidal positional encoding. This uses sine and cosine functions at different frequencies across the embedding dimensions, following the formula from the original "Attention Is All You Need" paper. The key advantage over learned positional embeddings is that it requires no additional parameters and generalises to sequence lengths not seen during training.

[Task 2 — Decoder Block and Causal Masking (Phase 4)]
The model consists of 8 stacked DecoderBlocks. Each block applies pre-layer normalisation before multi-head self-attention with 6 heads, then adds the residual, applies another layer norm, and passes through a feed-forward network with a 4× hidden expansion and GELU activation. The most critical component is the causal attention mask — an upper triangular boolean matrix that blocks every position from attending to any future position. Without this mask the model would see future tokens during training and would learn nothing meaningful — it would trivially copy the next token. This causal mask is what makes the architecture a decoder and not an encoder.

[Task 3 — Training Loop and Optimisation (Phase 5)]
The final model has approximately 15 million trainable parameters. For optimisation I used AdamW with a weight decay of 0.01. Weight decay acts as L2 regularisation and prevents the weights from growing excessively. Gradient clipping is applied at norm 1.0 before every update — this prevents exploding gradients, which are common in transformer training on small datasets. Every fixed number of steps the model is evaluated on the validation set, and both validation loss and perplexity are logged. Training stops automatically when the validation loss falls below a threshold or the maximum step count is reached. The entire model state plus the hyperparameter configuration is saved as artifacts_group1/decoder_only_15m.pt. Saving the config alongside the weights allows the model to be reconstructed for inference without passing command-line arguments.

[Justification of Inferences]
The model's outputs demonstrate that training succeeded in learning the statistical patterns of the domain corpus. Terms like "annex", "paragraph 3", "correction vehicle", "vmax", "km", "test", and "speed" appear repeatedly across all five generated samples. The lower-than-expected fluency is consistent with a 15M model trained on a single regulatory document. Larger corpora and more parameters would improve fluency, but within the assignment scope the model has demonstrably learned the domain vocabulary distribution — which is the core objective of pre-training.

[Task 1 — Autoregressive Inference]
After loading the checkpoint from artifacts_group1/decoder_only_15m.pt, the model generates text in an autoregressive loop — one token at a time. At each step, the model produces logits over the entire vocabulary for the next position. These logits are scaled by a temperature parameter to control randomness. I used top-k sampling with k=40: only the top 40 most probable tokens are kept and re-normalised, from which the next token is sampled. I also applied a repetition penalty to reduce the probability of any token that has already appeared in the generated sequence — preventing endless loops. Additionally, a no-repeat n-gram constraint prevents the model from repeating any phrase of N tokens that has already been generated.

[Task 2 — Five Inference Examples and Analysis]
I ran five diverse prompts and saved the outputs to evaluation/demo_5_predictions.txt. The prompts test different registers: policy language, contract language, compliance requirements, risk management, and report conclusions. Looking at the outputs, several observations justify that the model has learned from the domain corpus. First — domain vocabulary appears consistently. Terms such as "annex", "paragraph 3", "correction vehicle", "vmax", "km", "test", "vehicles", and "speed" appear across every single generated sample — confirming the model absorbed the domain vocabulary. Second — regulatory citation patterns emerge. The model generates phrases like "paragraph 3" and "annex" followed by identifiers, mirroring the citation style in AIS 175. Third — limitation acknowledgement: the outputs are not fully grammatical sentences. This is expected for a 15M model trained on a single regulatory document. Our goal was to demonstrate the pre-training pipeline end-to-end, and the domain signal is clearly present in every output.

[Task 3 — RAG Question-Answering Pipeline]
Beyond generation, the system also includes a retrieval-augmented Q&A mode. I implemented answer_from_corpus(), which first applies an intent mapping: a curated table of question themes — scope, road load family, gear selection, OBD, RDE, evaporative emissions — each mapped to specific section anchors in the clean corpus. If a question matches a known intent, the function retrieves the actual passage and returns it as the answer — no hallucination, pure extractive retrieval. For questions outside the intent map, a keyword-scored fallback ranks all sentences in the corpus and returns the top matches. This makes the Q&A reliable for factual regulatory queries.
